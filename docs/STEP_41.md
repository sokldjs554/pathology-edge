# 41단계: 슬라이드 끝에서 실제 읽기 크기를 사용하는 이유

상태: **사용자 해석 예정**. [40단계](STEP_40.md)의 함수 본문과 사용자 `8 passed in 7.08s` 보고를 확인했습니다. Codex는 제출 본문을 그대로 반영해 계약 8개·전체 175개 통과를 확인했습니다. 실제 WSI 읽기부터 사용자 좌표 함수·패치 영역 생성까지 7조건을 실행하고, native ROI 3개의 저장 패치 960개와 대조했습니다. 이 실행은 Codex 기여이며 사용자 실제 WSI 실행으로 기록하지 않습니다.

## 지금 확인할 사례 하나

CMU 원본의 오른쪽 아래를 읽은 실제 메타데이터입니다. 추가 다운로드·갱신·테스트 실행 없이 아래 자료로 설명하면 됩니다.

| 항목 | 실제 값 |
|---|---|
| 원본 슬라이드 크기 | `(46000, 32893)` |
| ROI 원점, level-0 좌표 | `(45970, 32870)` |
| 선택 level / 실제 downsample | `0` / `1.0` |
| 요청한 읽기 크기 | `(128, 128)` |
| 경계에서 잘린 뒤 실제 읽기 크기 | `(30, 23)` |
| 리사이즈 후 모델 입력 크기 | `(15, 46)` |

**질문:** 모델 입력의 오른쪽 아래 경계점 `(15, 46)`은 원본의 어느 좌표가 되어야 하나요? 리사이즈 비율을 계산할 때 요청 크기 `(128, 128)` 대신 실제 읽기 크기 `(30, 23)`을 써야 하는 이유와 함께 설명해 주세요.

한 답변으로 좌표와 이유를 보내면 됩니다. 픽셀 경계점이므로 마지막 픽셀 중심/인덱스를 구하는 질문은 아닙니다. 사용자 해석은 답변을 받은 후 U53에 기록합니다.

## 확인 범위

현재 확인한 경로는 `read_roi → RoiGeometry → roi_points_to_level0 → local_to_level0 → roi_patch_manifest`입니다. Codex가 제공한 읽기·crop·리사이즈와 사용자가 작성한 좌표 변환·연결 본문을 구분합니다. 기존 공개 native exporter와 저장 영상·모델 결과는 그대로입니다. 일반 배율 모델 추론, 핵 중심점의 half-pixel 보정, WSI 전체 분석·정답 기반 성능 검증을 새로 수행한 것은 아닙니다.
